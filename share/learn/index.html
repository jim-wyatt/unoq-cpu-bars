Arduino UNO Q — start here

You are reading this off the board itself. Everything below is on it too — no internet required.

1. The board is two computers

That is the single most useful thing to know. They sit on one PCB and talk over a serial link, but they run different operating systems and are good at different things.

MPU — Qualcomm QRB2210

Four ARM cores running Debian Linux. Python, web servers, AI models, networking, storage. This page is being served from it.

MCU — STM32U585

One Cortex-M33 running Zephyr. Real-time GPIO, sensors, actuators and the 8×13 LED matrix. No operating system getting in the way of a microsecond. 

   Linux (MPU)                         Zephyr (MCU)
   ───────────                         ────────────
   reads /proc/stat  ──── UART ────►   rasterises bars
   web server              lpuart1     drives 104 LEDs
   Python                /dev/ttyHS1   timer ISR, 10µs slots

3. The two GPIOs nobody documents

If the board ever looks dead after a reboot, it is almost always one of these. Two lines on the Linux side control the MCU, and they appear in no datasheet and in no Zephyr board definition.

gpiochip1FunctionSymptom when wrong
line 37 MCU BOOT0 Firmware flashes and verifies — but never runs. The STM32 boots its ROM bootloader instead.
line 70 UART link enable The MCU transmits happily and /dev/ttyHS1 reads zero bytes. Looks exactly like broken firmware. It is not.

Set them by hand with:

gpioset -c /dev/gpiochip1 -t0 37=0    # BOOT0 low
gpioset -c /dev/gpiochip1 -t0 70=1    # UART link on
BOOT0 is latched at reset. Set it before resetting or flashing the MCU, not after — the STM32 only samples that pin as it comes out of reset.

4. Talk to the MCU

From a shell on the board:

tio /dev/ttyHS1 -b 115200     # the Zephyr shell, interactively
unoq:~$ app status            # uptime, panel orientation, refresh sweeps
unoq:~$ app bars 30 60 90 20  # draw four bars on the LED matrix

Or from Python:

from unoq import MCU, CpuSampler

with MCU() as mcu:
    print(mcu.status())
    mcu.bars(CpuSampler().sample())   # CPU load, one bar per core
One process at a time owns that port. If you get "device busy", something else has it — usually the CPU-bars service. sudo systemctl stop unoq-cpu-bars frees it.

5. The LED matrix

104 blue LEDs in an 8×13 grid, charlieplexed across eleven pins (PF0–PF10). Only one LED is physically lit at any instant — the picture you see is entirely persistence of vision, refreshed from a timer interrupt every 10 µs.

That gives ~962 sweeps per second. Brightness is duty cycle: a level-3 pixel is driven in 3 of every 7 sweeps. app status reports the sweep count, which is the only way to tell from the far end of a serial cable that the panel is really being driven.
